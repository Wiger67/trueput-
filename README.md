# trueput

輕量、方法透明的網路速度測試工具，用 Rust 撰寫。測下載、上傳，以及負載下延遲（bufferbloat）。
單一執行檔約 2.5 MB。

## 使用

```bash
cargo build --release
./target/release/trueput                 # Cloudflare：下載 + 上傳 + 延遲
./target/release/trueput -b all          # 所有伺服器依序測試並比較
./target/release/trueput -b ndt7         # M-Lab ndt7（附伺服器端 TCPInfo 交叉驗證）
./target/release/trueput -t download     # 只測下載（download / upload / both）
./target/release/trueput -c 4            # 固定 4 條連線（預設 auto）
./target/release/trueput --no-early-stop # 一定測滿 --duration（預設 15 秒）
./target/release/trueput --json          # JSON 輸出（含所有樣本與量測）
```

## 測量方法

所有後端、兩個方向都用同一套引擎（`src/engine.rs`），結果可以直接互相比較。

### 速度

1. **平行連線**：單一條 TCP 常被視窗大小、伺服器限速卡住，所以開多條；連線數預設自動調整（見下方）。
2. **不寫硬碟、不壓縮**：下載的資料計數後直接丟掉；上傳用不可壓縮的隨機資料。
3. **暖機**：TCP 慢啟動、連線數調整期間的資料不列入。暖機要「至少 3 秒」**而且**「連線數已鎖定」才結束。
4. **主要結果 = 暖機後的總位元組 ÷ 暖機後的時間。** 這就是那段期間實際的傳輸量。
   - 為什麼不用短樣本的中位數？作業系統的 socket 緩衝區會讓資料「一陣一陣」地送（上傳特別明顯：核心要等緩衝區空出一大半才喚醒程式），200ms 的樣本可能一半是 0、一半是兩倍，中位數會嚴重失真。總量 ÷ 時間不受這個節奏影響，因為緩衝區在暖機時已經填滿，開始與結束時的緩衝量互相抵銷。
   - 在本機以伺服器實際收到的位元組對照，上傳主要結果誤差在 ±5% 以內。
5. **起伏**：每 200ms 取一次「最近 1 秒的平均速度」，報告 P10–P90 與中位數，只用來描述穩定程度。正式樣本的窗格不會跨進暖機期。
6. **提前結束**：正式量測至少 4 秒後，若最近 2 秒內主要結果（累積平均）的變化小於 2%（上傳 3%），代表再測下去結果也不會改變，就提前結束。上限為 `--duration`，而且會剛好在上限結束。
   - 上傳放寬到 3%：上傳的資料隨 socket 緩衝區一批一批交出，累積平均呈鋸齒狀，振幅約「一批的大小 ÷ 已傳總量」，用 2% 要多等好幾秒才會收斂。
7. 數值是應用層 goodput，不含 TCP/IP/TLS 標頭，約比線路速度低 3–6%。

### 動態調整連線數

做法（`src/autoscale.rs`）：

1. 從 2 條開始，每個評估窗格看一次速度。
2. 第一次評估直接把連線數加倍試試看；之後只要速度比上一個窗格高 **10% 以上**，就繼續加倍（2 → 4 → 8 → 16）。
3. 速度沒有明顯成長，或到達上限（`--max-connections`，預設 16），就鎖定。
4. 測試時間過半還沒鎖定，就強制鎖定，確保有足夠的正式樣本。
5. **評估窗格依延遲調整**：`max(1 秒, 10 × 閒置 RTT)`，上限 3 秒。高延遲路徑的慢啟動要好幾個 RTT 才跑得起來，太短的窗格會誤判「加連線沒幫助」。上傳因為緩衝區節奏，窗格至少 2 秒。

用 `-c <N>` 可以改成固定連線數；ndt7 依規範固定 1 條（輸出會顯示「1（ndt7 規範固定 1 條）」）。

### 延遲與 bufferbloat

- **量法**：對測速伺服器建立 TCP 連線，量三向交握（SYN → SYN-ACK）的時間。只量網路來回時間，不含 TLS 與伺服器處理；DNS 事先解析，不算在內。
- **閒置延遲**：每台伺服器測試前量 10 次（間隔 100ms），下載與上傳共用。
- **負載下延遲**：下載、上傳期間各自每 250ms 量一次（`--latency-interval-ms`），暖機期的量測不列入統計。上傳的 bufferbloat 通常比下載嚴重，值得分開看。
- **Bufferbloat 等級**：依「傳輸中延遲中位數 − 閒置延遲中位數」評分：<5ms A+、<30 A、<60 B、<200 C、<400 D、其餘 F。
- 若閒置量測全部失敗（例如防火牆擋掉額外的連線），會略過負載下量測，測速照常進行。
- 量測與傳輸跑在同一個 runtime 上；CPU 很弱的機器跑高速傳輸時，排程延遲可能讓延遲數值略微偏高。

### 伺服器端交叉驗證（ndt7）

ndt7 伺服器會定期回報核心的 TCPInfo。我們用它來對照客戶端的結果：

- **速度**：正式量測期間，伺服器確認的位元組數（下載用 `BytesAcked`、上傳用 `BytesReceived`）÷ 伺服器端時間，並顯示客戶端與它的差距。
- **RTT**：傳輸中那條連線的核心平滑 RTT，可以和 TCP 交握量到的負載下延遲互相印證。

### 多伺服器比較

`-b all`（或 `-b cloudflare,ndt7`）會依序測試每台伺服器，最後列出比較與差異百分比。
**差異超過 10% 時，瓶頸很可能在你到特定伺服器的路徑上，而不是你自己的網路**——這也是單一測速網站（例如只連 Netflix CDN 的 fast.com）可能「不準」的原因。

## 後端

| 後端 | 協定 | 連線數 | 上傳 | 伺服器端量測 | 備註 |
|---|---|---|---|---|---|
| `cloudflare` | HTTP/1.1 `GET /__down`、`POST /__up` | 自動 | ✓ | — | 非正式 API，可能被修改或限流 |
| `ndt7` | WebSocket，M-Lab 開放協定 | 固定 1 條 | ✓ | TCPInfo | 每個方向約 10 秒，伺服器由 locate API 選擇 |

新增後端只要實作 `src/backend/mod.rs` 裡的 `Backend` trait。

## 專案結構

```
src/
├── main.rs            CLI 參數與流程（多後端、雙向）
├── engine.rs          測速引擎：平行連線、取樣、暖機、提前結束、伺服器端對照
├── autoscale.rs       動態調整連線數、依 RTT 決定評估窗格
├── latency.rs         延遲量測（TCP 交握）
├── stats.rs           統計、bufferbloat 等級、穩定判斷
├── report.rs          人類可讀 / JSON 輸出、多伺服器比較
└── backend/
    ├── mod.rs         Backend trait、共用 HTTP client、隨機資料
    ├── cloudflare.rs
    └── ndt7.rs
```

## 已知限制

- Cloudflare 上傳沒有伺服器端回報，只能用客戶端「交給 socket 的位元組」計算；靠暖機與總量 ÷ 時間抵銷緩衝區效應，短時間的起伏（P10–P90）仍會偏寬。要最準的上傳數字，請對照 ndt7 的伺服器端結果。
- 延遲量測固定使用 DNS 解析出的第一個 IP；若傳輸走的是另一個協定（IPv4 / IPv6），兩者量的不是同一條路徑。
